# MedFlow AI

**AI Hospital Load Intelligence · GovTech Camp Kazakhstan, Case 1**

Локальный работающий MVP для анализа нагрузки на стационары и доступа к плановой госпитализации. Система читает предоставленные государственные CSV, проверяет качество, связывает ожидающих с направлениями, обучает CatBoost и показывает измеренные результаты в Streamlit. Это инструмент управленческой аналитики; он не ставит диагнозы и не даёт пациентам медицинских рекомендаций.

## Быстрый запуск

Проверено на Windows, Python 3.13.1. Работайте из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m src.train_waiting_model
.\.venv\Scripts\python.exe -m streamlit run app.py
```

Откройте http://localhost:8501. Команда обучения сама подготовит отсутствующие или устаревшие данные. Обработка и обучение выполняются локально, без облачного API. Для воспроизводимого окружения этого запуска можно установить `requirements-lock.txt` вместо `requirements.txt`.

В созданном окружении доступен короткий запуск:

```powershell
.\run.ps1
```

Скрипт проверяет актуальность данных/модели, при необходимости готовит их, затем запускает приложение. Для принудительного переобучения: `.\run.ps1 -Retrain`.

Другие команды:

```powershell
.\.venv\Scripts\python.exe inspect_data.py
.\.venv\Scripts\python.exe -m src.preprocessing --force
.\.venv\Scripts\python.exe -m src.aggregation
.\.venv\Scripts\python.exe -m pytest -q
```

## Проблема и решение

Очереди, направления, отказы и пролеченные случаи поступают отдельными выгрузками. Руководителю трудно сопоставить данные и увидеть рост нагрузки. MedFlow объединяет только записи с проверенной связью, даёт агрегированную историю по организациям и регионам, оценивает типичное ожидание до госпитализации и показывает статистические отклонения активности.

## Предоставленные данные

Результат полной проверки первоначальных CSV от 11 сентября 2026; приложение пересчитывает эти показатели из файлов:

| Источник | Строк | Период / ограничение |
|---|---:|---|
| Ожидающие | 765 182 | Регистрация 01.01–31.03.2025; 20 регионов, 1 406 кодов организаций |
| Направления | 255 710 | Регистрация 01.01–31.03.2025; **часть 1 из 3**, 572 организации |
| Отказы приёмного покоя | 251 456 | События 01.01–31.03.2025; **часть 1 из 6**, 71 организация |
| Пролеченные случаи | 2 196 | 2 193 уникальных названия организаций; дата выгрузки 30.04.2026, отчётный период неизвестен |

CSV можно класть в `data/` или `data/raw/`. Имена с кириллицей, пробелами и суффиксом `(1)` поддерживаются. Обнаружение использует заголовки CSV, поэтому автоматически включает новые `part_002`, `part_003` и последующие части. Покрытие частей определяется по именам. Не кладите вторую копию файла без необходимости. Сравнение списка файлов, размера и времени изменения обнаруживает обновления; это быстрый индикатор версии, не криптографическая проверка содержимого.

После добавления файлов нажмите **Prepare / refresh data** и переобучите модель на странице **Model performance**, либо повторите команду обучения. Пока модель устарела, прогнозы заблокированы; старые показатели явно помечаются.

## Архитектура

```text
CSV (data/ + data/raw/)
  → DuckDB: дисковая обработка и проверки
  → очищенные Parquet + отчёт качества
       ├─ whitelist признаков → временной split → CatBoost + median baseline
       ├─ hospital × day → история, статистические аномалии, prototype pressure
       └─ SQL-агрегаты → Streamlit + Plotly
```

| Модуль | Назначение |
|---|---|
| `src/data_loader.py` | Обнаружение частей, CSV dialect, строковые коды, ограниченный DuckDB |
| `src/data_quality.py`, `inspect_data.py` | Полная проверка столбцов, пропусков, диапазонов дат и уникальных значений |
| `src/preprocessing.py` | Очистка, контроль неоднозначных ключей, соединение, Parquet |
| `src/feature_engineering.py` | Общая подготовка признаков для обучения и прогноза |
| `src/train_waiting_model.py`, `src/predict.py` | Обучение, метрики, сохранение и загрузка CatBoost |
| `src/aggregation.py`, `src/anomaly_detection.py` | Дневные агрегаты и индикаторы относительно предыдущих наблюдений |
| `src/dashboard_data.py`, `src/ui.py`, `app.py` | Агрегированные запросы и интерфейс |

DuckDB использует дисковую промежуточную БД и лимит **1 GB**; тяжёлые операции удаления дублей выполняются одним потоком. Лимит DuckDB не ограничивает всю память процесса Python. В pandas передаётся только проекция признаков для CatBoost или небольшие агрегаты для графиков, а не все исходные CSV. Настройки — `src/config.py`; при необходимости задайте `MEDFLOW_MEMORY_LIMIT`, например `2GB`. `MEDFLOW_DATA_DIR` позволяет выбрать другую папку данных.

## Качество данных и связь

Коды читаются строками, включая начальные нули. Ключ ожидающих:

```text
region_origin_code + "." + mo_destination_code + "." + profile_code + "." + patient_seq_no
```

На исходной первой части все 255 710 направлений имеют совпадение. Проверка уникальности дополнительно выявила 21 неоднозначный ключ ожидающих и 509 повторяющихся ключей направлений с различающимися записями. 1 018 направлений с конфликтующими ключами помещены в `referral_key_quarantine.parquet`; основной аналитический набор содержит 254 692 строки. Это предотвращает размножение строк при соединении. Неоднозначные ожидающие не участвуют в обогащении; направления сохраняются с отсутствующими полями связанного источника. Точные дубли бизнес-записей, кроме времени выгрузки, удаляются с учётом в отчёте.

Границы допустимых дат и ожидания вынесены в конфигурацию. Неразбираемые даты, sentinel-значения и даты вне заданных границ становятся пропусками. Плановая дата сравнивается с регистрацией по календарному дню, чтобы полночь того же дня не считалась ошибкой. Фактическая госпитализация раньше точного времени регистрации признаётся недостоверной для target. Первоначально найдено 35 525 таких строк; они не превращаются в нулевое ожидание. Одновременные госпитализация/отказ помечаются конфликтом. Ожидание свыше 90 дней не участвует в ML, но корректное событие сохраняется в аналитике.

Внутренний SHA-256 исходных бизнес-полей сохраняет различие между записями, даже если разные ошибочные даты после очистки стали одинаковыми пропусками. Он не является признаком модели и не выводится в интерфейс.

`data/processed/data_quality_report.json` содержит пропуски, исходные диапазоны, неправильные даты, связи, исключения, полноту источников и правила. `inspection_report.json` — отдельный отчёт команды первичной проверки. Исходные CSV не изменяются. Отказы и пролеченные случаи сохраняются отдельно: достоверного межтабличного ключа для них нет. Идентичные строки этих источников лишь отмечаются, поскольку без ключа события нельзя доказать, что они дубли.

## Модель и проверка

Target: `(hospitalization_dt − registration_dt)` в дробных днях. Используются только наблюдённые, непротиворечивые госпитализации с `0 ≤ wait_days ≤ 90`. Начальная очистка дала 191 020 подходящих строк; среднее 6,126 дня, медиана 0,726 дня.

Признаки: организация, ICD-10, профиль койки, территориальный тип, цель направления, источник финансирования и календарь регистрации. Коды госпитализаций, patient_seq_no, исходы, planned_dt и сведения о пролеченных случаях 2026 года не используются как признаки.

Ранние 80% **уникальных дат регистрации** образуют окно обучения; последние 20% — тест. Граница не подбирается по качеству модели. Из раннего окна также удаляются примеры, чей исход ещё не был известен к началу теста. На первоначальных файлах: 148 974 обучающих, 29 423 тестовых примера; 12 623 ранних примера исключены из-за позднего исхода. Тест не используется для выбора параметров или early stopping.

CatBoost: 300 деревьев, глубина 6, learning rate 0.06, MAE loss, фиксированный seed. Эта модель оценивает **типичное, условно-медианное** ожидание среди подходящих госпитализированных, а не математическое ожидание срока для всех направленных пациентов. Baseline всегда предсказывает медиану обучающей выборки.

Метрики **MAE**, **RMSE**, **baseline MAE** и `(baseline MAE − model MAE) / baseline MAE × 100%` вычисляются каждым запуском обучения. Отрицательное улучшение не скрывается. Проверенные результаты находятся в `models/model_metadata.json` и на странице **Model performance**; интерфейс не переобучает модель при каждом переключении вкладки. Модель — `models/waiting_time_catboost.cbm`. Actual vs Predicted показывает агрегированные группы ожидания, не отдельные направления; группы меньше 10 записей исключены.

Финальный проверенный запуск на первоначальных CSV, тест регистрации **14–31 марта 2025**:

| Метрика | Результат |
|---|---:|
| CatBoost MAE | 5,6287 дня |
| CatBoost RMSE | 13,3823 дня |
| Медианный baseline MAE | 6,3295 дня |
| Улучшение MAE | 11,07% |

Это измерения конкретного запуска, а не обещание качества. Больший RMSE показывает наличие крупных ошибок. Порядок обучающих строк фиксирован перед CatBoost, чтобы порядок вывода SQL не менял результат перестроения. После загрузки сохранённого CBM метрики повторно пересчитаны на всём тесте и совпали с metadata.

## Историческая нагрузка и ограничения

- Это выгрузки прошлого периода. Ожидающие в исходном файле не равны очереди на сегодня. «No recorded outcome» означает отсутствие исхода в предоставленных направлениях, а не подтверждённый текущий статус пациента.
- Направления первой части охватывают 8 связанных регионов происхождения, хотя полный источник ожидающих содержит 20. Частичные данные нельзя экстраполировать на всю страну.
- Среднее ожидание и качество модели относятся только к наблюдённым допустимым госпитализациям. Исключение отказов, незавершённых и аномальных записей создаёт смещение отбора; есть проблема цензурирования исходов.
- Некоторые исходы относятся к 2026 году. Исторические графики показывают их на фактической дате события; фильтр регистрации выбирает когорту и не меняет дату её исходов.
- Дневная открытая когорта = накопленные допустимые регистрации минус известные к данной дате выходы, только в предоставленных частях. Начальная очередь до периода неизвестна. Это не занятость коек; конфликтные и недостоверные исходы исключены из реконструкции.
- Prototype pressure сравнивает направления, отказы и открытую когорту с предыдущими 28 календарными днями при минимуме 14 дней истории: HIGH выше p95, MEDIUM выше p75, иначе LOW. Это выбранные описательные пороги, не калиброванный риск. Аномалия роста очереди оценивается по положительному дневному изменению. Текущий день не включается в базу сравнения.
- **Prototype risk indicator — not yet clinically/operationally validated.** Нет данных о коечном фонде, реальной пропускной способности и полной очереди. Числовой прогноз нагрузки на 7/30/90 дней не опубликован: этот модуль ещё не обучен и не проверен. Приложение прямо сообщает его состояние.
- Одна временная проверка не подтверждает переносимость модели в 2026 год, причинность признаков или медицинскую эффективность. Внешняя валидация и интервалы неопределённости ещё нужны.

В интерфейсе нет patient-level идентификаторов, строк пациентов и выгрузок направлений. CSV, Parquet и CBM исключены из Git. Локальные производные файлы всё ещё следует рассматривать как данные проекта; MVP не включает промышленную авторизацию, контроль доступа и журнал действий.

## Demo за 30–45 секунд

1. **Overview** — реальные числа, период и покрытие частей.
2. **Hospital explorer** — выбрать организацию и показать историю событий.
3. **Waiting time prediction** — заполнить профиль и нажать **Estimate waiting time**.
4. **Model performance** — показать MAE, baseline, временной тест и ограничения.

Текст трёхминутного выступления и запросы на поддержку — в `docs/DEMO.md`.

## Дальнейшие шаги

1. Добавить оставшиеся части, согласовать словари организаций, проверить случаи неоднозначных ключей и восстановить полноту событий.
2. Получить определения временных полей, историю очередей и исходов, фактический коечный фонд по профилям, ограничения мощности и длительность пребывания.
3. Провести несколько последовательных временных backtests, оценить ошибки по организациям/профилям, учесть незавершённые исходы и калибровать неопределённость.
4. Проверить сезонный/наивный baseline нагрузки на 7 дней; расширять горизонты только при достаточной истории и качестве. Сначала определить измеримый target нагрузки.
5. При необходимости вынести модули подготовки/прогноза в FastAPI, а интерфейс в React; добавить авторизацию, версионирование, мониторинг drift и аудит.
