# План авторизации, RBAC и первого входа в MedFlow AI

Дата: 26 сентября 2026 года. Статус: основная хакатонная версия реализована. По уточнению заказчика используется PostgreSQL. [Настройка и команды](AUTH_SETUP.md). Веб-админка отложена в пользу CLI; публичная часть — описание и методология без открытых бизнес-API.

## 1. Что должно получиться

Посетитель открывает понятную страницу с объяснением назначения MedFlow AI и кнопкой входа. После входа сервер определяет роль и доступные организации. Сотрудник больницы сразу видит свою больницу, сотрудник госоргана — разрешённую ему сводку. Выбирать себе роль пользователь не может.

RBAC отвечает за доступные действия, а область доступа (scope) — за организации, над которыми эти действия разрешены. Скрытые кнопки дополняют серверные проверки, но не заменяют их.

**Подтверждено заказчиком:** демонстрация на хакатоне с тестовыми аккаунтами; публичная часть доступна любому посетителю; сотрудники входят в личный кабинет; госорган видит все больницы, сотрудник больницы — только свою.

**Предлагаемые технические решения:** вход по логину и паролю, серверные cookie-сессии, две аналитические роли и служебная роль администратора. Под публичной частью в этом плане понимаются описание продукта, объяснение показателей и вход, без текущих аналитических API. Открытые статистические дашборды потребуют отдельного решения о составе публикуемых данных.

Под «простым человеком» здесь понимается новый посетитель, который ещё не знаком с продуктом. Личный кабинет пациента, запись на госпитализацию и публичный доступ к аналитике в этот план не включены.

## 3. Путь пользователя и дизайн

### До входа

Новый маршрут `/#welcome`, без запросов к аналитическим API:

- Логотип, заголовок «Госпитальная аналитика для больниц и органов здравоохранения».
- Короткое объяснение: «Анализируйте направления, наблюдаемое ожидание и прогноз входящего потока».
- Два информационных блока: что получает сотрудник больницы и что получает госорган. Эти блоки не назначают роль и не открывают рабочие кабинеты.
- Главная кнопка «Войти в рабочий кабинет» → `/#login`.
- Подсказка «Доступ выдаёт администратор вашей организации». Реальный контакт добавляется после уточнения; не создавать неработающую форму запроса доступа.
- Блок «Как читать показатели»: направления, медиана ожидания, прогноз потока простыми словами; без запроса закрытых данных.
- Ясная подпись о текущем историческом периоде и назначении продукта: это аналитика, а не сервис записи пациента или текущая очередь.

Для хакатона рядом со входом можно показывать явно обозначенные тестовые учётные записи, включаемые только конфигурацией демо. Вход всё равно проходит через обычный `/api/auth/login`, роль берётся из БД. Демо-режим не отключает RBAC и не даёт браузеру назначать произвольную роль. Публикация тестовых паролей фактически открывает доступ к соответствующей демонстрационной аналитике всем посетителям, поэтому по умолчанию реквизиты выдаются участникам отдельно; блок открытых реквизитов — только при явном выборе такого формата показа.

Страница входа: логин, пароль, показать/скрыть пароль, состояния отправки и ошибки. Поля «Выберите роль» нет. Восстановление доступа в первой локальной версии — через администратора; самостоятельное восстановление добавляется только вместе с рабочим механизмом доставки.

### После входа

| Пользователь | Стартовая страница | Навигация |
|---|---|---|
| Сотрудник больницы | «Обзор моей больницы», название закреплённой организации и понятные следующие действия | Обзор, Моя больница, Прогнозы, Как читать показатели |
| Аналитик госоргана | Национальный обзор всех больниц | Обзор, Стационары, Сравнение, Прогнозы, Как читать показатели |
| Администратор платформы | Пользователи и доступ | Пользователи, Организации, Журнал доступа, Состояние системы |

Вместо переключателя «Госорган / Больница» — имя пользователя, роль, организация и действие «Выйти». Длинные названия организаций переносить или сокращать с доступом к полному названию; сохранить исправление карточки «Изменения».

Для больницы убрать глобальный поиск организаций. Если позже разрешены несколько больниц — показывать выбор только из серверного списка; при единственной организации селектор не нужен.

После первого входа показать небольшой закрываемый блок из 2–3 подсказок, без обязательного многошагового тура. Например: «Посмотрите динамику направлений», «Откройте прогноз», «Узнайте, как читать оценку ожидания». Настройка закрытия относится к конкретному пользователю.

Технические инструкции про CSV, пути и команды перенести в административный раздел. Сотрудникам оставить дату данных, статус доступности прогноза и объяснения показателей.

### Состояния, которые нужно спроектировать

- Проверка сессии: нейтральный экран загрузки без краткого показа общего дашборда.
- Неверный логин или пароль: единое сообщение без раскрытия существования аккаунта.
- Истекшая сессия: форма входа с объяснением и возвратом на разрешённую внутреннюю страницу.
- Вход выполнен, но организация не назначена: «Доступ ещё не настроен», без подстановки чужой больницы.
- Доступ есть, данных нет: отдельное состояние с периодом и разрешёнными фильтрами.
- Нет доступа к разделу: сообщение и переход на собственный обзор.
- Сервер недоступен: предложить повторить запрос; не выдавать сетевую ошибку за выход из аккаунта.

## 4. Предлагаемая матрица прав

Роли первой версии: `government_analyst`, `hospital_analyst`, `platform_admin`. Посетитель без сессии — состояние, а не назначаемая роль. В первой версии один пользователь имеет одну роль; произвольный конструктор ролей не нужен.

| Действие | Посетитель | Госорган | Больница | Администратор |
|---|---|---|---|---|
| Прочитать описание продукта / войти | Да | Да | Да | Да |
| Обзор и показатели | Нет | В своей области доступа | Только своя больница | Нет по умолчанию |
| Каталог и сравнение больниц | Нет | В своей области доступа | Нет | Нет по умолчанию |
| Карточка больницы | Нет | Разрешённые организации | Только своя | Нет по умолчанию |
| Прогноз потока и оценка ожидания | Нет | Разрешённые организации | Только своя | Нет по умолчанию |
| Публичные объяснения показателей | Да | Да | Да | Да |
| Методология и метрики качества действующих моделей | Нет | Да | Да | Да |
| Техническая диагностика и покрытие исходников | Нет | Нет | Нет | Да |
| Создание / блокировка пользователей, назначение роли и организации | Нет | Нет | Нет | Да |
| Просмотр журнала доступа | Нет | Нет | Нет | Да |

Администратор управляет учётными записями, но не получает аналитические данные автоматически. Для демонстрации аналитики используется отдельный тестовый аккаунт. Возможность одновременного совмещения ролей — отдельное расширение.

Права выразить именованными действиями: `overview:read`, `hospital:read`, `hospital:list`, `comparison:read`, `forecast:read`, `waiting:predict`, `methodology:read`, `system:read`, `users:manage`, `organizations:manage`, `audit:read`. Отображение роли в UI не используется как доказательство права в API.

## 5. Архитектура авторизации

### Учётные записи и хранение

По уточнению заказчика реализована отдельная PostgreSQL-база `medflow` с версионируемыми миграциями. Она не заменяет Parquet/DuckDB аналитики. Подключение хранится в локальном `.env` вне Git; используется отдельная роль приложения без прав суперпользователя.

Минимальные сущности:

| Сущность | Основные поля / назначение |
|---|---|
| `users` | ID, нормализованный уникальный логин, имя, хеш пароля, роль, статус, требование смены пароля, версия прав |
| `organizations` | Стабильный ID, тип (госорган/больница), отображаемое название, статус |
| `hospital_bindings` | Связь организации с точным `hospital_mo` в текущей выгрузке; при необходимости несколько подтверждённых вариантов названия |
| `user_hospital_access` | Разрешённые больницы пользователя; в первом MVP у сотрудника больницы ровно одна |
| `government_scopes` | Явно выданная национальная область либо перечень подведомственных организаций |
| `sessions` | Хеш случайного идентификатора сессии, пользователь, сроки действия, отзыв, CSRF-контекст |
| `audit_events` | Субъект, действие, объект, время, результат; без паролей, токенов и содержимого медицинских форм |

Названия организаций сейчас служат идентификаторами в URL и API. В новом контракте использовать стабильный `hospital_id`, а точное исходное название разрешать только внутри сервера. Старые ссылки можно переводить в ID лишь после проверки доступа. Переименование или новая выгрузка не должны автоматически привязывать пользователя к похожему названию.

Пустой перечень разрешений означает отсутствие доступа. Национальная область выдаётся явно и никогда не выводится из пустого списка.

### Сессия

Для текущей схемы «React и API на одном origin» предлагается серверная сессия с непрозрачным случайным ID в `HttpOnly` cookie. Это позволяет отзывать доступ при блокировке пользователя без ожидания истечения автономного токена.

- `Secure` в окружении HTTPS, `SameSite=Lax`, ограниченная область cookie; для локального HTTP — явная настройка разработки. Небезопасный режим не должен включаться автоматически в опубликованном окружении.
- Предварительные сроки: 30 минут бездействия и 8 часов абсолютной жизни; сделать настраиваемыми. Фоновое обновление данных не должно бесконечно продлевать бездействующую сессию.
- Менять ID при входе; отзывать сессии при выходе, блокировке, смене пароля и изменении прав. На каждом запросе проверять актуальный статус пользователя и версию прав.
- Пароли хешировать Argon2id через поддерживаемую библиотеку; не хранить пароль или токен входа в `localStorage`.
- Защищать POST/PATCH/DELETE от CSRF, включая вход/выход: проверка Origin и токен; отдельно продумать получение токена до входа. CORS не считать заменой CSRF.
- Ограничить частоту попыток входа; не логировать введённые секреты. Для локального одного процесса допустим локальный лимитер; для нескольких экземпляров нужен общий счётчик.

Практики cookie и отзыва сессий сверяются с [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), защита изменяющих запросов — с [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Пример интеграции хеширования и зависимостей приведён в [документации FastAPI](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/); JWT из примера не является обязательным выбором для проекта.

### Серверные границы доступа

Последовательность запроса: **сессия → действующий пользователь → разрешённое действие → область организаций → проверка выбранного объекта → запрос/прогноз → ответ**.

Для списков и сводок серверный scope пересекается с фильтрами пользователя до агрегации, сортировки, вычисления `total` и пагинации. Пользовательские фильтры могут только сужать выборку. Проверки доступа по умолчанию запрещают действие, если разрешение не выдано; проверяются все запросы, как рекомендует [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

Ввести транспортно-независимый `DataScope` и общий построитель ограничений в аналитическом слое. Не импортировать FastAPI или сессии в ML. В inference передавать уже проверенную больницу. Сохранить проверки малых групп и существующие ограничения интерпретации прогнозов.

## 6. API: что закрываем и что добавляем

| Маршрут | План |
|---|---|
| `GET /api/auth/me` | Текущий пользователь, роль, права, организация, разрешённая стартовая страница; 401 без сессии |
| `GET /api/auth/csrf` | Получение CSRF-контекста; не выдаёт аналитические данные |
| `POST /api/auth/login` | Проверка учётных данных, новая сессия; клиент не назначает роль или организацию |
| `POST /api/auth/logout` | Отзыв сессии на сервере и удаление cookie |
| `POST /api/auth/change-password` | Смена временного/текущего пароля, проверка текущих полномочий и отзыв старых сессий |
| `/api/admin/users`, `/api/admin/organizations`, `/api/admin/audit` | Минимальное управление доступом и просмотр аудита; только соответствующие административные права |
| `/api/bootstrap` | Только после входа; допустимые фильтры, период и сводка в scope; для администратора отдельный минимальный контекст без аналитики |
| `/api/overview` | Ограничить stats, trend, attention и расчёт границ периода одним scope |
| `/api/hospitals`, `/api/compare` | Только госорган; поиск, выбранные группы, `total`, результаты — внутри scope |
| `/api/hospital/overview`, `/api/hospital/forecast` | Проверять `hospital_id` до чтения данных и запуска модели |
| `/api/wait-options`, `/api/predictions/wait` | Проверять организацию и в query, и в JSON; не подставлять глобальную больницу при пропущенном значении |
| `/api/models` | Техническую сводку оставить администратору; выделить минимальный `/api/methodology` для аналитиков |
| `/api/health` | Только минимальный статус процесса без периодов, путей, сводок и метаданных; подробная готовность — в защищённой диагностике |
| `/docs`, `/redoc`, `/openapi.json` | Отключить или ограничить в опубликованном окружении; оставить для локальной разработки |

401 означает отсутствие действующей сессии; 403 — запрет функции для роли. Для недоступной/неизвестной больницы возвращать одинаковый 404, без раскрытия её существования. Административные ошибки не должны показывать хеши, внутренние пути или содержимое БД.

Отдельно проверить утечки через справочники, fallback-категории `/wait-options`, `featured_hospital`, метаданные качества и кеши. Общие категории модели допустимы только как явно утверждённый неперсональный справочник, а не как неявный возврат данных других больниц. Кеш scoped-ответов учитывает версию данных и нормализованную область доступа; HTTP-ответы с данными пользователя не кешируются публично.

Аутентификация и получение `/auth/me` должны работать, даже если аналитические файлы отсутствуют. Сейчас `ready()` относится к данным; переносить эту зависимость на вход нельзя.

## 7. Порядок реализации

### Этап 1. Уточнение политики и контрактов

Зафиксировать подтверждённые границы: национальная область у госоргана, одна больница у сотрудника, публичное описание без бизнес-API. Подготовить две тестовые привязки к существующим организациям A/B и аккаунты для обеих больниц, госоргана и администратора. Определить формат `User`, `Permissions`, `DataScope`, `hospital_id` и ошибок. Новые медицинские организации или пациентские записи для этого не создавать.

**Результат:** однозначно понятно, кому доступны какие данные; неоднозначные региональные права не подменены фильтром происхождения направления.

### Этап 2. Основа аккаунтов и сессий

Создать `backend/modules/auth/` (хранение, хеширование, сессии, политика) и отдельные HTTP-маршруты/зависимости в `backend/modules/`. Добавить миграции, конфигурацию и явную CLI-команду первоначального создания администратора. Пароль задаётся интерактивно/через защищённый локальный ввод, без общего пароля в репозитории. Демо-аккаунты создаются отдельной явной командой, не при старте сервера.

**Результат:** вход, восстановление сессии после обновления страницы, выход, смена временного пароля и отзыв доступа работают на сервере.

### Этап 3. Защита всех бизнес-маршрутов

Ввести общий механизм scope, применить его ко всем маршрутам из таблицы, кешам и справочникам. Перевести внешние ссылки на стабильные ID, добавить сопоставление с выгрузкой. Сохранить границы модулей и численные результаты для пользователя с полным разрешённым доступом.

**Результат:** сотрудник A не получает данные B через прямой HTTP-запрос, пропущенный фильтр, замену ID или запрос прогноза. Защита работает независимо от фронтенда.

### Этап 4. Новый первый вход и кабинеты

Вынести из `App.tsx` компоненты `AuthProvider`, `PublicLayout`, `WelcomePage`, `LoginPage`, `ProtectedRoute`, `AppShell`, `UserMenu`. В `api.ts` добавить типизированные ошибки и работу с сессией/CSRF. Запрос `/bootstrap` выполнять только после успешного `/auth/me`.

Удалить `medflow-mode` и переключатель. Меню и стартовые страницы строить по правам. При выходе, смене пользователя и отзыве доступа отменять запросы и очищать показанные данные; запоздавший ответ прошлого аккаунта не должен заполнить новый кабинет. Обработать выход в другой вкладке. Проверять внутренний адрес возврата после входа; внешний `returnTo` не принимать.

Сделать первый экран, вход и короткое введение в том же визуальном стиле. Отдельно проверить мобильный размер, клавиатуру, подписи полей, сообщения об ошибках и длинные названия больниц.

**Результат:** новый посетитель понимает назначение продукта, а вошедший пользователь сразу попадает в свой рабочий контекст.

### Этап 5. Выдача аккаунтов для хакатона

Обязательный минимум: CLI-команды создания/просмотра пользователей, назначения роли и больницы, блокировки, сброса пароля и отзыва сессий. Добавить воспроизводимую команду подготовки тестовых аккаунтов, не перезаписывающую существующие пароли и назначения без явного запроса оператора. Не разрешать удалить/заблокировать последнего действующего администратора или случайно лишить его административной роли. Смена прав отзывает старые сессии.

Веб-страницы администрирования и `/api/admin/*`, описанные выше, — следующий приоритет после работающих двух кабинетов; их можно вынести за пределы обязательного хакатонного результата. Если они отложены, не выводить пустой административный кабинет и не выпускать незащищённые заглушки маршрутов. Управление выполняет локальный оператор через CLI.

Для демо достаточно выдачи учётных данных оператором. Email-приглашения, самостоятельный сброс по почте, SSO и MFA для пилота планируются отдельно после выбора инфраструктуры; не показывать фиктивно работающие кнопки.

**Результат:** тестовые аккаунты воспроизводимо создаются, доступ можно выдавать и отзывать без редактирования БД вручную. Веб-админка не задерживает основной демонстрационный сценарий.

### Этап 6. Проверки и документация

Добавить HTTP-тесты авторизации и изоляции, проверить пользовательские сценарии в браузере, выполнить существующие Python-тесты и production-сборку React. Обновить `README.md`, `docs/WEB_INTERFACE.md`, `docs/ARCHITECTURE.md`, инструкции запуска и переменные окружения. Весь веб-доступ должен проходить через защищённый API.

**Результат:** воспроизводимый запуск, тестовые аккаунты без секретов в Git и подтверждённая матрица доступа.

## 8. Критерии приёмки

1. Без входа посетитель видит описание и форму входа; бизнес-API отвечает 401, включая справочники и прогнозы.
2. Роль невозможно повысить заменой `localStorage`, hash-маршрута, query, JSON или заголовка. Самостоятельный выбор роли отсутствует.
3. Больница A видит только свои показатели. Проверены A→B запросы ко всем объектным маршрутам, в том числе подмена `hospital_mo` в прогнозе ожидания.
4. Отсутствие hospital-фильтра, пустые разрешения, неизвестный ID и удалённая привязка не раскрывают глобальную сводку.
5. В bootstrap, поиске, счётчиках, attention и кеше нет организаций вне scope. Два пользователя, последовательно использующие один процесс и браузер, не получают ответы друг друга.
6. Госорган получает только явно разрешённую область; если первая версия национальная, это отражено в учётной записи и названии кабинета.
7. Оператор может создать и заблокировать пользователя через CLI; при реализации веб-админки это доступно только администратору. Административная роль не получает аналитические права автоматически. Последний администратор защищён от случайной блокировки.
8. Logout, истечение срока, смена пароля, блокировка и изменение роли реально закрывают доступ по старой cookie. Проверены вход с фиксацией сессии, CSRF и ограничение попыток входа.
9. При отказе сети не происходит ложный logout; после настоящего 401 прошлые данные больше не показываются. Кнопка «Назад», новая вкладка и повторный вход не восстанавливают чужой кабинет.
10. Проверка входа работает при неготовых аналитических данных; пользователь видит отдельное объяснение недоступности аналитики.
11. На первом экране за несколько секунд понятно назначение продукта, кому он предназначен и как войти. В кабинете видно, от чьего имени и по какой организации идёт работа.
12. Вёрстка проверена на широком экране и телефоне; прежнее исправление карточки «Изменения» сохранено. Расчёты и существующие тесты аналитики не регрессируют.

## 9. Решения заказчика и оставшиеся уточнения

Уже согласовано: хакатон, тестовые аккаунты, публичная часть для посетителей, национальный доступ госоргана, доступ сотрудника только к своей больнице. Повторного подтверждения этих решений не требуется.

| Вопрос | Предлагаемый вариант до уточнения | Что меняется при другом ответе |
|---|---|---|
| Публичная часть — описание продукта или ещё и открытые статистические дашборды? | Описание, объяснения показателей и вход | Для публичной статистики нужен отдельный ограниченный API; текущие бизнес-маршруты остаются защищёнными |
| Какие две больницы использовать для тестовых аккаунтов? | При реализации выбрать две существующие организации с данными для показа; зафиксировать их ID | При указании конкретных больниц использовать их, проверить наличие истории и прогнозов |
| Реквизиты тестовых аккаунтов показывать на странице входа? | Выдать отдельно участникам демонстрации | Открытые реквизиты дают посетителям доступ к демонстрационной аналитике соответствующей роли |
| Нужна ли веб-админка именно к показу? | Достаточно CLI и подготовленных аккаунтов | Добавится отдельный интерфейс управления пользователями и его HTTP-тесты |
| Хакатонный показ будет только локально или по публичной ссылке? | Локально, как сейчас | Публичный запуск требует HTTPS, постоянного хранилища сессий и проверки настройки cookies; публично доступный legacy-интерфейс исключается |

Эти уточнения не мешают подготовке основы: для реализации можно использовать предложенные варианты, если заказчик не задаст другие.

## 10. Границы первой версии

План не требует переобучения ML, изменения медицинских расчётов или публикации исходных данных. Пока не включены открытая регистрация, социальный вход, произвольные роли, кабинет пациента, межбольничные рейтинги для сотрудников и интерфейс запуска обучения.

Рекомендуемый порядок работы: **политика доступа → серверная сессия → изоляция данных → интерфейс входа и кабинеты → управление аккаунтами → сквозная проверка**. Переносить защиту API на этап после косметической замены переключателя нельзя.
