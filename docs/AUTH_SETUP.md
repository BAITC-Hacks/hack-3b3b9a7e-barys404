# Авторизация и PostgreSQL

PostgreSQL хранит пользователей, организации, сессии, CSRF-токены, ограничения входа и журнал событий. Аналитические выгрузки остаются в Parquet/DuckDB. Docker для локального запуска не нужен.

## Первый запуск

1. Запустите PostgreSQL 17+, установите `requirements-api.txt`.
2. Создайте `.env` по образцу `.env.example`: `MEDFLOW_DATABASE_URL` указывает отдельную базу и пользователя без прав суперпользователя. Зарезервированные символы пароля в URI нужно URL-кодировать.
3. Если базы ещё нет, временно задайте `MEDFLOW_ADMIN_DATABASE_URL` на служебную базу `postgres` и выполните `python -m scripts.setup_auth_db`. Команда создаст `medflow` и роль `medflow_app`, сохранит строку приложения и уберёт административную строку. Существующую базу/роль она не перезаписывает.
4. Выполните:

```bash
python -m scripts.auth migrate
python -m scripts.auth seed-demo
npm --prefix frontend run build
python -m scripts.serve
```

На Windows используйте `.venv\Scripts\python.exe` вместо `python`. Данные должны быть подготовлены перед `seed-demo`; см. [README](../README.md). Миграции выполняются явно, под транзакционной блокировкой PostgreSQL. Обычный запуск не создаёт аккаунты.

Откройте `http://127.0.0.1:8000/#welcome`; `/#login` открывает вход. Кабинет определяется серверной ролью. Vite проксирует `/api`; локально разрешены Origin на портах 8000 и 5173.

## Тестовые аккаунты

| Логин | Доступ |
|---|---|
| `government.demo` | Все больницы, каталог, сравнение, прогнозы |
| `hospital.a` | Первая выбранная для демо больница |
| `hospital.b` | Вторая больница, без доступа к первой |
| `admin.demo` | Служебная страница и методология; без аналитических прав |

Случайные пароли и точные организации сохраняются в `.runtime/demo-accounts.md` и JSON для локальной проверки. Эти файлы не раздаются сервером и исключены из Git вместе с `.env`. Не публикуйте реквизиты. Повторный `seed-demo` создаёт только отсутствующие аккаунты, не меняет пароли и назначения существующих. Потерянный пароль заменяется через `reset-password`.

## Управление

```bash
python -m scripts.auth users
python -m scripts.auth organizations
python -m scripts.auth create-user analyst --name "Имя сотрудника" --role hospital_analyst --hospital-id UUID
python -m scripts.auth create-user government --name "Аналитик" --role government_analyst
python -m scripts.auth disable analyst
python -m scripts.auth enable analyst
python -m scripts.auth assign analyst --role hospital_analyst --hospital-id UUID
python -m scripts.auth reset-password analyst
python -m scripts.auth revoke analyst
python -m scripts.auth audit
```

Пароль вводится интерактивно. Обычный новый аккаунт и сброс требуют смены пароля при входе; демо-аккаунты готовы к показу. Изменение роли, больницы, пароля или статуса отзывает сессии. Последнего активного администратора нельзя отключить или лишить роли. Веб-админка отложена; управление выполняет оператор CLI.

После обновления выгрузки выполните `python -m scripts.auth sync-organizations` и перезапустите API до возобновления доступа. При точном совпадении названия ID сохраняется; исчезнувшая организация деактивируется. При переименовании оператор явно назначает новую привязку через `assign`.

## Границы защиты

- Каждый запрос проверяет сессию, разрешение и больницу. Национальная область есть только у `government_analyst`. Внешние объектные запросы принимают `hospital_id`; названия разрешает сервер. Чужая и неизвестная больницы дают одинаковый 404.
- Пропущенный фильтр сотрудника означает его больницу. Bootstrap, справочники и кеш ограничены этой же организацией. `/api/models` доступен администратору; `/api/methodology` намеренно отдаёт общие метрики обеим аналитическим ролям.
- Сигналы, качество данных и PDF наследуют область организации. Чужой ID проверяется до чтения агрегатов. Национальный перечень источников в `/api/quality` виден только госоргану. `/api/validation` намеренно показывает общие ошибки, но группы сотрудника ограничены его больницей даже при запросе другой группировки. Администратор не имеет разрешений `signals:read`, `quality:read`, `validation:read`, `briefing:export`.
- PDF принимает только ID разрешённых больниц, фильтры и фиксированный вопрос; клиент не передаёт итоговые цифры или метрики. Сервер требует `reviewed: true` и контрольную сумму актуального просмотра. Смена контекста, данных, модели или пользователя требует нового просмотра. Это защита от случайного использования устаревшей сводки, не доказательство прочтения или электронная подпись. Выход из аккаунта отменяет и запоздавшие ответы с PDF.
- Пароли: Argon2id. ID сессий и CSRF хранятся в БД как SHA-256-хеши. Cookie сессии — HttpOnly, SameSite=Lax; API-ответы — `Cache-Control: no-store`.
- Срок сессии: 8 часов, простой: 30 минут. `/auth/me` не продлевает её; POST активности отправляется при действии пользователя не чаще раза в минуту.
- POST требуют разрешённый Origin и привязанный к сеансу CSRF-токен. Вход ограничен 10 попытками на логин и 60 на IP за 15 минут.
- Выход отзывает сессию; межвкладочное событие и проверка при фокусе/раз в минуту очищают кабинет. Запоздавшие ответы прошлого аккаунта отбрасываются.
- `/api/health` сообщает только состояние процесса. Вход не зависит от аналитических файлов.

Для публичного окружения задайте `MEDFLOW_ENV=production` и `MEDFLOW_ORIGINS=https://ваш-домен`: включатся Secure cookies с префиксом `__Host-`, документация API отключится. Нужны HTTPS, постоянная PostgreSQL и резервное копирование. Старый Streamlit — только локальный инструмент оператора без RBAC; не публикуйте его рядом с защищённой платформой.

## Проверка

```bash
python -m pip install -r requirements.txt
python -m pytest -q
npm --prefix frontend run build
```

HTTP-тесты создают отдельную случайную PostgreSQL-схему `test_auth_*` и удаляют только её. Рабочие таблицы не очищаются. Требуется право создания схем; CI использует отдельную PostgreSQL. Без `MEDFLOW_DATABASE_URL` эти тесты пропускаются, поэтому для полной проверки соединение обязательно.
