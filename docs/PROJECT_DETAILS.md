# MedFlow AI

**AI Hospital Load Intelligence · GovTech Camp Kazakhstan, Case 1**

Локальный работающий MVP для анализа нагрузки на стационары и доступа к плановой госпитализации. Система читает предоставленные государственные CSV, проверяет качество, связывает ожидающих с направлениями, обучает CatBoost и показывает измеренные результаты через React и FastAPI. Это инструмент управленческой аналитики; он не ставит диагнозы и не даёт пациентам медицинских рекомендаций.

## Веб-интерфейс

В `frontend/` находится интерфейс React, а `backend/api/main.py` отдаёт ему агрегированные показатели и прогнозы через HTTP. Готовая сборка обслуживается одним локальным Python-процессом на **http://127.0.0.1:8000**. Аккаунты, сессии и права доступа хранятся в PostgreSQL; настройка описана в [AUTH_SETUP.md](AUTH_SETUP.md).

Если окружение и подготовленные данные уже есть:

```bash
.venv/bin/python -m pip install -r requirements-api.txt
cd frontend
npm ci
npm run build
cd ..
MEDFLOW_MEMORY_LIMIT=2GB .venv/bin/python -m uvicorn backend.api.main:app --host 127.0.0.1 --port 8000
```

На Windows замените `.venv/bin/python` на `.venv\Scripts\python.exe` и задайте лимит памяти через `$env:MEDFLOW_MEMORY_LIMIT="2GB"`. Если данных ещё нет, положите исходные CSV в `data/raw/` и один раз запустите `python -m scripts.bootstrap` из виртуального окружения до запуска сайта. Эта подготовка обрабатывает большие файлы и может занять время; при обычном запуске веб-интерфейса она не повторяется.

Для разработки можно запустить `npm run dev` в `frontend/` после старта API и открыть http://127.0.0.1:5173. Описание экранов, API и ограничений: [docs/WEB_INTERFACE.md](WEB_INTERFACE.md).

Материалы показа: [презентация](presentations/MedFlowAI_Final_2026-10-02.pptx), [офлайн-слайды](presentations/MedFlowAI_Offline_Slides.html). Актуальный сценарий работы описан в [WEB_INTERFACE.md](WEB_INTERFACE.md).

## Быстрый запуск

На Windows работайте из корня проекта, Python 3.12+ и Node.js 22+:

```powershell

.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
npm --prefix frontend ci

# Сначала настройте PostgreSQL и MEDFLOW_DATABASE_URL в .env.
```

Откройте http://127.0.0.1:8000. Обработка и обучение выполняются локально, без облачного API. `requirements-lock.txt` фиксирует версии зависимостей для CI/демо; `requirements.txt` задаёт допустимые диапазоны для окружения разработчика.

Перед демонстрацией проверьте готовность данных и моделей командой `python -m scripts.demo_check`. Она не обучает модели и не проверяет браузерный интерфейс. После первоначальной установки зависимостей, настройки локальной PostgreSQL и подготовки артефактов приложение и презентация работают без интернета.

## Проблема и решение

Очереди, направления, отказы и пролеченные случаи поступают отдельными выгрузками. Руководителю трудно сопоставить данные и увидеть рост нагрузки. MedFlow объединяет только записи с проверенной связью, даёт агрегированную историю по организациям и регионам, оценивает типичное ожидание до госпитализации и показывает статистические отклонения активности.

Не кладите вторую копию файла без необходимости. Полнота частей означает наличие всех файлов с указанной нумерацией, а не подтверждённую полноту национальной статистики. Дополнительные онкологические и вакцинационные CSV не включаются в эти модели. Новые госпитальные части расширили охват организаций, но период регистрации остался прежним: 90 дней.

## Архитектура

```text
CSV (data/ + data/raw/)
  → DuckDB: дисковая обработка и проверки
  → очищенные Parquet + отчёт качества
       ├─ whitelist признаков → временной split → CatBoost + median baseline
       ├─ hospital × day → история, статистические аномалии, prototype pressure
       ├─ hospital × day → фиксированная дата прогноза → CatBoost на 7 дней + два baseline
       └─ SQL-агрегаты → FastAPI → React
```

| Модуль | Назначение |
|---|---|
| `backend/data_pipeline/data_loader.py` | Обнаружение частей, CSV dialect, строковые коды, ограниченный DuckDB |
| `backend/data_pipeline/data_quality.py`, `scripts/inspect_data.py` | Полная проверка столбцов, пропусков, диапазонов дат и уникальных значений |
| `backend/data_pipeline/preprocessing.py` | Очистка, контроль неоднозначных ключей, соединение, Parquet |
| `ml/feature_engineering.py` | Общая подготовка признаков для обучения и прогноза |
| `ml/train_waiting_model.py`, `ml/predict.py`, `ml/waiting_estimator.py` | Обучение, метрики и единый расчёт ожидания: групповые медианы + CatBoost для редкой истории |
| `ml/load_forecast.py` | Прототип 7-дневного прогноза входящих направлений по организациям |
| `ml/validation.py` | Повторные обучения на трёх окнах, метрики по группам и горизонтам без изменения действующих моделей |
| `ml/explanations.py` | SHAP для веток CatBoost; основание и число случаев для групповых оценок |
| `scripts/demo_check.py` | Проверка готовности данных, моделей и временной валидации без переобучения |
| `frontend/src/pages/`, `frontend/src/widgets/` | Страницы React: обзор, карточка стационара, сравнение, прогнозы и администрирование |
| `backend/analytics/briefing.py` | Одностраничный PDF с кириллицей |

| `backend/auth/`, `backend/api/auth.py`, `backend/api/admin.py` | Аккаунты PostgreSQL, сессии, роли и управление доступом |

DuckDB использует дисковую промежуточную БД и лимит **2 GB**; тяжёлые операции удаления дублей выполняются одним потоком. Лимит DuckDB не ограничивает всю память процесса Python. В pandas передаётся только проекция признаков для CatBoost или небольшие агрегаты для графиков, а не все исходные CSV. Настройки — `backend/core/config.py`; при необходимости задайте `MEDFLOW_MEMORY_LIMIT`, например `1GB` или больше для крупной выгрузки. `MEDFLOW_DATA_DIR` позволяет выбрать другую папку данных.

## Качество данных и связь

Коды читаются строками, включая начальные нули. Ключ ожидающих:

```text
region_origin_code + "." + mo_destination_code + "." + profile_code + "." + patient_seq_no
```

Все 767 130 исходных направлений имеют совпадение ключа с ожидающими. Удалены 1 758 точных дублей бизнес-записей, кроме времени выгрузки. Обнаружены 21 неоднозначный ключ ожидающих и 1 969 конфликтующих ключей направлений; 3 938 строк направлений помещены в `referral_key_quarantine.parquet`. В аналитическом наборе осталось **761 434 уникальных направления**, 1 382 организации и 20 регионов. Все оставшиеся направления однозначно связались с ожидающими; расхождений календарной даты регистрации нет. Проверено равенство: 767 130 = 1 758 дублей + 3 938 строк карантина + 761 434 аналитических строк. Это предотвращает размножение строк при соединении. Неоднозначные ожидающие не участвуют в обогащении; в общем случае направления без однозначной связи сохраняются с отсутствующими полями связанного источника.

Границы допустимых дат и ожидания вынесены в конфигурацию. Неразбираемые даты, sentinel-значения и даты вне заданных границ становятся пропусками. Плановая дата сравнивается с регистрацией по календарному дню, чтобы полночь того же дня не считалась ошибкой. Фактическая госпитализация раньше точного времени регистрации признаётся недостоверной для target. В полных исходных направлениях найдено 105 260 таких строк; они не превращаются в нулевое ожидание. Одновременные госпитализация/отказ помечаются конфликтом. Ожидание свыше 90 дней не участвует в ML, но корректное событие сохраняется в аналитике.

Внутренний SHA-256 исходных бизнес-полей сохраняет различие между записями, даже если разные ошибочные даты после очистки стали одинаковыми пропусками. Он не является признаком модели и не выводится в интерфейс.

`data/processed/data_quality_report.json` содержит пропуски, исходные диапазоны, неправильные даты, связи, исключения, полноту источников и правила. `inspection_report.json` — отдельный отчёт команды первичной проверки. Исходные CSV не изменяются. Отказы и пролеченные случаи сохраняются отдельно: достоверного межтабличного ключа для них нет. Идентичные строки этих источников лишь отмечаются, поскольку без ключа события нельзя доказать, что они дубли.

## Модель и проверка

Target: `(hospitalization_dt − registration_dt)` в дробных днях. Используются только наблюдённые, непротиворечивые госпитализации с `0 ≤ wait_days ≤ 90`. Очистка расширенного набора дала 554 416 подходящих строк; среднее 6,946 дня, медиана 0,934 дня.

Признаки: организация, ICD-10, профиль койки, территориальный тип, цель направления, источник финансирования и календарь регистрации. Коды госпитализаций, patient_seq_no, исходы, planned_dt и сведения о пролеченных случаях 2026 года не используются как признаки.

Ранние 80% **уникальных дат регистрации** образуют окно обучения; последние 20% — тест. Граница не подбирается по качеству модели. Из раннего окна также удаляются примеры, чей исход ещё не был известен к началу теста. На расширенном наборе: 426 465 обучающих, 86 341 тестовый пример; 41 610 ранних примеров исключены из-за позднего исхода. Тест не используется для выбора параметров или early stopping.

Версия ожидания v3 использует иерархическую групповую оценку: медиана обучающей истории «стационар × профиль» при ≥10 случаях, затем медиана стационара при ≥10 случаях. Для редких известных стационаров используется CatBoost (300 деревьев, глубина 6, learning rate 0.06, MAE, seed 42). Отрицательный выход CatBoost и новые стационары получают явно обозначенную оценку по обучающей истории профиля или всей выборки, не произвольный положительный порог. Это **типичное, условно-медианное** ожидание среди подходящих госпитализированных, не индивидуальный срок для всех направленных пациентов. Baseline всегда предсказывает общую медиану обучающей выборки. Выбор правила сделан на внутреннем временном окне до 14 марта, без использования финального теста регистрации 14–31 марта.

Метрики **MAE**, **RMSE**, **baseline MAE** и `(baseline MAE − model MAE) / baseline MAE × 100%` вычисляются каждым запуском обучения. Отрицательное улучшение не скрывается. Проверенные результаты находятся в `models/model_metadata.json` и на странице **Качество модели**; интерфейс не переобучает модель при каждом переключении вкладки. Модель — `models/waiting_time_catboost.cbm`. Actual vs Predicted показывает агрегированные группы ожидания, не отдельные направления; группы меньше 10 записей исключены.

Проверенный запуск 26 сентября 2026 на всех трёх частях направлений, тест регистрации **14–31 марта 2025**:

| Метрика | Результат |
|---|---:|
| Групповая оценка + CatBoost MAE | 5,2709 дня |
| Групповая оценка + CatBoost RMSE | 12,0445 дня |
| Прежний CatBoost MAE на том же тесте | 6,5133 дня |
| Медианный baseline MAE | 7,1198 дня |
| Улучшение MAE к общему baseline | 25,97% |

Это измерения конкретного запуска, а не обещание качества. Больший RMSE показывает наличие крупных ошибок. На тесте 84 384 оценки основаны на стационаре и профиле, 1 762 — на стационаре, 134 — на CatBoost, 61 — на истории профиля. Интерфейс не скрывает, что почти все оценки здесь групповые. Порядок обучающих строк фиксирован. Для воспроизведения нужен CBM вместе с обучающими агрегатами `calibration` в metadata; один CBM не воспроизводит итоговую v3. Оценка и метрики используют одну функцию `calibrated_predictions`.

Прежние MAE 5,63 / baseline 6,33 относились к первой части. Состав и размер теста изменились, поэтому это не сравнение двух моделей на одинаковой выборке.

## Прогноз входящих направлений на 7 дней

Временная проверка исправлена: **одна дата начала прогноза — конец 24 марта 2025**, тест — **25–31 марта**. Обучение использует только целевые значения по 24 марта включительно. Каждая организация получает ровно семь прогнозов из одной и той же наблюдённой истории; фактические значения тестовой недели не попадают в признаки. Раньше проверка смешивала даты начала прогноза до границы обучения и внутри тестовой недели; прежние метрики этого модуля не подходят для оценки исправленного протокола.

Признаки: организация, горизонт, день недели целевой даты, последние наблюдённые значения и средние за 7/14/28 дней. День начала прогноза включён в историю. Это семь прямых прогнозов; предсказания не подставляются обратно в признаки. Для обучения и проверки нужны минимум 42 календарных дня. Пропуски дней и повторные пары «организация × день» отклоняются; нулевые дни формируются явно на этапе агрегации.

Обучение: **503 048 примеров**. Тест: **9 674 пары «организация × день»**, 1 382 организации, исключённых организаций нет. Один обученный CatBoost сохраняется без дообучения на тесте, поэтому опубликованные метрики воспроизводятся именно из сохранённого CBM.

| Метрика на финальной неделе | Направлений на организацию в день |
|---|---:|
| CatBoost MAE | 3,6027 |
| CatBoost RMSE | 8,2210 |
| Baseline: среднее последних 7 наблюдённых дней | 5,2655 MAE |
| Baseline: тот же день предыдущей недели | 5,3585 MAE |

Улучшение к среднему за 7 дней — **31,58%**. Оно не равномерно: на горизонте одного дня MAE модели **6,46**, baseline **3,31**. Метрики каждого горизонта показаны отдельно в интерфейсе и metadata; параметры по этому тесту не подбирались.

Модель: `models/referral_load_7day_catboost.cbm`; протокол, версии данных и метрики: `models/referral_load_7day_metadata.json`; проверочные агрегаты: `models/referral_load_7day_catboost.validation.parquet`. Старые модели с прежним протоколом, изменённые исходные данные, незавершённая подготовка и изменённые агрегаты блокируют прогноз. Следующие семь дней в текущем наборе — **1–7 апреля 2025**, а не текущая неделя 2026 года.

## Повторная проверка и объяснение прогнозов

Выполнено по **три непересекающихся тестовых окна** с расширяющейся историей обучения и фиксированными параметрами. Суммарный MAE ожидания v3 **5,3261 дня** против медианного baseline **6,9698** на 241 702 наблюдениях. Ранние окна пересекаются с данными внутреннего выбора правила: это исследовательская повторная проверка, не независимое подтверждение выбранного метода. Для потока MAE **3,5489** против **5,4964** у среднего за 7 дней и **4,7760** у сезонного baseline на 29 022 парах «организация × день». Подробный протокол, все окна и ограничения: [результаты валидации](VALIDATION_RESULTS.md).

Эти результаты показаны на **Проверка по периодам**, включая ошибки по регионам/организациям/профилям и горизонтам. Они относятся к отдельным повторным обучениям, а не заменяют показатели финальных CBM выше. Небольшие группы исключаются; P90 ошибки не является персональным интервалом прогноза. После изменения данных отчёт помечается устаревшим и должен быть пересчитан.

SHAP показывается только для прогнозов, реально сделанных CatBoost. Для групповых оценок ожидания показываются основание, число обучающих случаев и дата отсечения; диагноз, цель и дата регистрации не меняют такую медиану. Вклады CatBoost не приписываются другому методу. SHAP объясняет поведение модели, но не устанавливает причинность.

## Сравнение и проверка человеком

**Сравнение и отчёт** сравнивает до шести организаций или регионов происхождения за общий период регистрации с общим фильтром профиля. Доступны объёмы, медиана/P90 допустимого наблюдённого ожидания, доля отказов среди известных исходов и недельная динамика. Минимальный размер группы задаётся явно; отсутствие достаточного количества наблюдений не заменяется нулём. Регион происхождения направления не считается адресом стационара. Сравнение не скорректировано на тяжесть случаев и доступную мощность.

Аналитик выбирает вопрос для проверки специалистом и подтверждает просмотр периода, области сравнения и ограничений перед выгрузкой агрегированной сводки в PDF или JSON. PDF содержит график, показатели, ошибку актуальных сохранённых моделей и версию источников. При изменении фильтров, групп, минимального размера, вопроса или версии данных требуется новое подтверждение. Автоматического исполнения управленческих решений нет. Это локальное подтверждение в сессии, не промышленное согласование с авторизацией и аудитом.

## Историческая нагрузка и ограничения

- Это выгрузки прошлого периода. Ожидающие в исходном файле не равны очереди на сегодня. «No recorded outcome» означает отсутствие исхода в предоставленных направлениях, а не подтверждённый текущий статус пациента.
- Все пронумерованные госпитальные части загружены; очищенные направления охватывают 20 связанных регионов происхождения. Это само по себе не доказывает полноту всех событий в стране.
- Среднее ожидание и качество модели относятся только к наблюдённым допустимым госпитализациям. Исключение отказов, незавершённых и аномальных записей создаёт смещение отбора; есть проблема цензурирования исходов.
- Некоторые исходы относятся к 2026 году. Исторические графики показывают их на фактической дате события; фильтр регистрации выбирает когорту и не меняет дату её исходов.
- Дневная открытая когорта = накопленные допустимые регистрации минус известные к данной дате выходы, только в предоставленных частях. Начальная очередь до периода неизвестна. Это не занятость коек; конфликтные и недостоверные исходы исключены из реконструкции.
- Prototype pressure сравнивает направления, отказы и открытую когорту с предыдущими 28 календарными днями при минимуме 14 дней истории: HIGH выше p95, MEDIUM выше p75, иначе LOW. Это выбранные описательные пороги, не калиброванный риск. Аномалия роста очереди оценивается по положительному дневному изменению. Текущий день не включается в базу сравнения.
- **Prototype risk indicator — not yet clinically/operationally validated.** Нет данных о коечном фонде, реальной пропускной способности и полной очереди. Доступен только начальный 7-дневный прогноз *входящих направлений* по организациям: это не прогноз занятости коек, госпитализаций, персонала или полной очереди. Он проверяется на последних семи исторических днях и требует внешней валидации. Прогнозы на 30/90 дней не публикуются.
- Проверки на одном историческом периоде не подтверждают переносимость модели в 2026 год, причинность признаков или медицинскую эффективность. Внешняя валидация и интервалы неопределённости ещё нужны.

В интерфейсе нет patient-level идентификаторов, строк пациентов и выгрузок направлений. CSV, Parquet и CBM исключены из Git. Локальные производные файлы всё ещё следует рассматривать как данные проекта. Веб-доступ ограничен сессией, ролью и организацией учётной записи; это не заменяет промышленную инфраструктуру безопасности и журнал действий.

## Demo за 30–45 секунд

1. **Обзор** — реальные числа, период и покрытие частей.
2. **Карточка стационара** — выбрать организацию и показать историю событий.
3. **Время ожидания** — заполнить профиль и нажать **Рассчитать ожидание**.
4. **Как читать показатели** — показать метрики, временной тест и ограничения.
5. **Прогнозы → Поток направлений** — выбрать организацию и показать прогноз входящих направлений на неделю с метриками временного holdout.

Описание экранов и сценария работы — в [WEB_INTERFACE.md](WEB_INTERFACE.md).

## Дальнейшие шаги

1. Согласовать словари организаций, проверить случаи неоднозначных ключей, восстановить полноту событий и получить более длинную историю.
